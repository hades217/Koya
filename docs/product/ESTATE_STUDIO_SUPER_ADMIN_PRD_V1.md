# Estate Studio Super Admin 与 CRM PRD

- 版本：V1.1
- 日期：2026-09-06
- 状态：待评审需求稿；本文不代表功能已开发或上线。
- 产品范围：平台负责人日常使用的 CRM 与全平台运营后台，覆盖客户、咨询、销售机会、跟进任务、注册账户和接入平台的 App 服务。
- 交付形态：独立 Web 管理后台，建议使用 `/admin` 路由，电脑浏览器优先，手机可查阅和处理咨询。
- 需求解释：将“资讯的用户”理解为“提交咨询、预约演示的用户”，即咨询线索；不是阅读资讯文章的访客。如实际指后者，需要另行定义内容浏览事件及匿名访客统计。

## 1. 产品目标

让平台负责人把 Super Admin 作为自己的 CRM，每天在这里查看客户、安排跟进、推进演示和报价、记录成交，并管理客户对应的 App 账户和服务。

第一版的核心业务闭环是：**官网咨询 / 手工录入 / 用户注册 → 统一客户档案 → 跟进和演示 → 销售机会与报价记录 → 成交或流失 → 持续服务与再次销售。** 注册可以发生在任意销售阶段，不是成交的前置条件，也不是成交证明。

统一客户档案是 CRM 的主入口：一个客户可有多次咨询、多条销售机会，并可关联一个注册账户。未注册也能成为客户，未咨询也能直接注册。咨询、账户状态、销售阶段分别保留；咨询提交不得自动创建登录账户或订阅。

## 2. 当前基础与新增需求

以下是本地仓库在本文编写时的情况，不是生产环境审计结论。

| 当前依据 | 已观察到的能力 | 对本需求的影响 |
| --- | --- | --- |
| 官网 `apps/estate-studio-website/public/app.js` | 预约表单生成发送至 `hello@estatestudio.io` 的邮件草稿，没有网络提交和存储 | 需要增加服务端咨询接收和持久化；点击邮件按钮不能记作成功咨询 |
| `apps/real-estate-ai-studio/gateway/README.md` 及网关代码 | 订阅激活码换取短期会话、额度和请求账本；存在服务端管理密钥 | 需要新增真正的用户身份体系和管理员权限体系；订阅记录不等于注册用户 |
| `apps/real-estate-ai-studio/README.md` | 桌面端项目库、授权和发布能力 | 本地项目和离线行为不会天然出现在云端后台；只展示已接入数据 |

官网现有邮件联系方案保持可用。本文提议把站内提交作为新增咨询入口，邮件作为备用联系渠道；这是后续实施范围，不在编写 PRD 时修改官网行为。历史邮件不会自动进入后台，首版允许管理员手工录入已实际收到的咨询并标明来源。

## 3. 用户角色和权限

首版只开放 Super Admin 后台账户；运营和只读角色放在下一阶段，权限模型预留支持。

| 角色 | 工作范围 | 权限边界 |
| --- | --- | --- |
| Super Admin，P0 | 全部客户、销售机会、跟进任务、注册用户、平台状态与设置、审计 | 平台范围；高风险操作必须确认并记录原因 |
| 运营管理员，P1 | 指定范围的咨询处理、基础用户查询 | 不可授予权限、调整计费或修改平台安全设置 |
| 只读管理员，P1 | 指定范围的数据查看 | 不可编辑、导出或查看未授权的联系方式 |
| 普通注册用户 | 正常使用客户 App | 无任何后台权限，不因属于客户公司的管理员而获得平台管理权限 |

首个 Super Admin 通过受控部署流程创建，禁止公开注册时选择管理员身份。首版后续管理员增减由受控运维完成；后台自助邀请、角色编辑在 P1 实现。任何流程都不得撤销最后一个可用 Super Admin。

## 4. 范围和导航

后台保留五个一级入口，首页默认进入“工作台”。客户、咨询和注册用户是同一客户中心的不同视图，不要求反复切换多个模块查同一个人。

| 导航 | P0 内容 | P1 扩展 |
| --- | --- | --- |
| 工作台 | 今日与逾期跟进、新咨询、近期机会、咨询及注册统计 | 趋势、转化分析、团队业绩 |
| 客户中心 | 全部客户、咨询记录、注册用户三个视图；统一档案、标签、基础公司资料、受控导入导出 | 负责人分配、组织权限、更多外部集成 |
| 销售机会 | 机会列表与看板、阶段、报价记录、成交与流失 | 自动化流程、报价文件生成、续费分析 |
| 平台管理 | 已接入服务健康状态、只读订阅及请求查询 | 云端项目与内容管理、公告、功能开关、计费操作 |
| 系统设置 | 管理员本人安全设置、咨询通知配置、时区、审计日志 | 管理员邀请、角色授权、更多集成设置 |

跟进任务从工作台集中查看，也能在客户和销售机会详情中创建。P0 先满足负责人自己管理客户和销售的日常需要，同时交付 App 账户管理；团队协作和复杂自动化放到 P1。“管理整个 App”的长期范围包括账户、组织、项目、内容、订阅、服务和配置；尚未同步的本地项目不属于后台可远程控制的对象。

## 5. 详细功能需求

### 5.1 登录与后台访问（P0）

- 管理员使用独立后台入口登录，启用 MFA；普通用户登录态不能访问后台。
- 所有后台接口在服务端校验当前账户状态、角色和数据权限，不只隐藏前端菜单。
- 超时退出、主动退出、密码或 MFA 恢复后的会话失效均有明确行为；建议空闲 30 分钟过期，最长会话 12 小时。
- 登录失败提示不暴露账户是否存在；登录和恢复流程具备速率限制。
- 后台不得显示密码、原始令牌、激活码、支付凭据或 provider 密钥。现有网关管理密钥只可用于服务端集成，不能交给浏览器。

### 5.2 工作台（P0）

首屏按“逾期跟进 → 今日跟进 → 待处理咨询 → 最近销售机会”排列，显示客户、下一步动作和截止时间；完成一项跟进后可立即安排下一次。统计卡片可以点击进入保持相同筛选条件的列表。

| 指标 | 定义 |
| --- | --- |
| 新增咨询数 | 所选时间内成功持久化的非垃圾咨询记录数；按咨询 ID 计数，不按人数 |
| 待处理咨询数 | 当前状态为“新咨询”的非垃圾记录总数，不受新增日期筛选限制 |
| 到期跟进数 | 到期且仍未完成的 FollowUpTask 数；按任务 ID 去重，不与咨询提醒重复计算 |
| 开放机会金额 | 当前非已成交、非已流失机会的预计金额，分币种汇总；未知金额单列机会数，不记作 0 |
| 已成交机会数与金额 | 按实际成交日期筛选已成交机会及约定金额，分币种汇总；不代表实际收款或会计收入 |
| 新注册用户数 | 所选时间内完成邮箱验证并正式建立的用户账户数 |
| 注册用户总数 | 正式注册且未匿名化删除的用户总数，包含禁用账户；展示统计更新时间 |

- 默认查看最近 7 天新增趋势，可选今天、近 30 天、自定义时间。
- 日期按后台设置时区计算，默认 `Australia/Brisbane`；存储使用 UTC，日期筛选采用开始时刻包含、结束时刻不包含。
- P0 不显示未经接入的 DAU、收入或本地项目数。接口异常显示“暂不可用”，从未接入显示“未接入”，只有查询成功且为空才能显示 0。
- 若部分数据源失败，其余数据仍可展示；失败卡片独立重试，并显示最近一次成功更新时间。

### 5.3 咨询管理（P0，最高优先级）

**列表字段**

咨询编号、姓名、邮箱、公司、需求摘要、来源、跟进状态、是否关联注册用户、最近跟进时间、下次跟进时间、提交时间。手机号只在实际提供时展示，不反推或补造。

**查找和筛选**

- 搜索姓名、邮箱、公司、咨询编号；按提交时间倒序默认排序。
- 按日期、来源、状态、是否关联注册账户、跟进是否到期筛选。
- 默认每页 25 条，可切换 50 条；使用服务端分页，筛选保存在 URL，详情返回后保留原列表位置。
- 垃圾咨询默认排除，可单独查看和恢复。

**详情内容与动作**

- 展示用户实际提交的完整咨询、联系方式、公司、提交入口、语言和时间。
- 时间线记录原始提交、状态变化、内部备注、账户关联和后续咨询，不覆盖原始文本。
- 管理员可添加内部备注、修改跟进状态、设置下次跟进时间、标记或恢复垃圾咨询。设置下次跟进创建或更新对应 FollowUpTask，咨询中显示该任务时间，不另建一套提醒。
- “发送邮件”在 P0 仅打开邮件客户端，不能自动写入“已联系”；由管理员实际联系后手工记录结果。自动邮件发送和邮箱同步不在 P0 范围。
- 可手工录入从现有邮箱等渠道实际收到的咨询，必填姓名、邮箱或手机号至少一个、咨询内容、收到时间、来源；记录录入人和系统创建时间。
- 历史补录同时保留 `received_at` 和 `created_at`，按实际收到时间进入历史咨询趋势，不能伪装成当天新获客。

**跟进状态**

| 状态 | 进入条件 |
| --- | --- |
| 新咨询 | 站内提交成功或新建手工记录 |
| 跟进中 | 管理员开始处理或已尝试联系 |
| 已安排演示 | 管理员填写双方已确认的演示时间 |
| 已完成 | 本次咨询已处理完毕，并填写处理结果 |
| 已关闭 | 暂无需求、无效联系方式等原因结束跟进，关闭原因必填 |

已完成和已关闭可重新打开为跟进中，必须填写原因；其他回退同样记录原因。“已注册”是独立关联标记，不属于跟进状态。用户注册不能自动把仍需回复的咨询关闭。“垃圾”是独立标记，不删除原记录。

**重复与注册关联**

- 同一次提交重试复用幂等键，只创建一条咨询；相同幂等键配不同内容返回冲突。
- 同一邮箱以后提交新的需求，建立新的咨询记录，详情中展示同邮箱历史；不得按邮箱直接吞掉后续需求。
- 注册邮箱验证成功后，使用已验证邮箱与咨询邮箱匹配并关联 `user_id`；关联仅用于运营查询，不向用户暴露未验证咨询中的历史内容。
- 邮箱比较去除首尾空格并按身份服务的统一规范处理，不自行删除 `+` 后缀或邮箱中的点。
- 邮箱不一致时由管理员核对后手工关联，理由必填且可撤销；不得根据姓名相同自动关联。
- 后续更换邮箱保持已建立的用户 ID 关系，不重新按旧邮箱把记录转给另一个账户；关联冲突进入人工核对。

### 5.4 注册用户管理（P0，最高优先级）

**注册定义与入口**

新增统一账户服务及可用注册入口；推荐首版采用邮箱验证链接完成注册与登录，降低密码支持负担。账户服务选型属于实施决策，不预设当前已接入某家供应商。

用户完成邮箱验证、接受当前服务条款后才计为“注册成功”。注册意向、咨询邮箱、订阅激活和本地许可证都不能直接计入注册人数。未验证申请单独记录状态和过期时间，不混入注册用户默认列表。

**列表字段与筛选**

- 字段：用户 ID、姓名（未提供则显示“未填写”）、邮箱、邮箱验证状态、账户状态、注册来源、注册时间、最后成功登录时间、关联咨询数。
- 已映射订阅时可显示订阅状态；未映射显示“未关联”，不能据此推断“免费用户”。
- 支持用户 ID、姓名、邮箱搜索；按注册时间、账户状态、注册来源筛选。P1 增加套餐和组织筛选。

**用户详情**

| 分区 | 内容 |
| --- | --- |
| 基本信息 | 用户 ID、姓名、邮箱、验证时间、账户状态、创建与更新时间 |
| 咨询历史 | 与该用户关联的咨询、状态及跳转入口 |
| 登录与安全 | 最后成功登录、账户状态变更、会话撤销记录；没有数据时明确说明 |
| 订阅与服务 | 已确认关联的订阅、额度、服务状态及数据来源；P0 只读 |
| 管理记录 | 内部备注、禁用与恢复原因、操作者和时间 |

**管理动作与边界**

- 禁用：确认具体用户并填写原因，阻止新登录及平台受保护服务请求，撤销现有在线会话；不删除咨询或账本。
- 恢复：重新允许登录与服务访问，不自动恢复旧会话，保留禁用历史。
- 单独撤销会话：账户仍有效，下次访问需要重新登录；操作记录原因。
- 管理员不得直接修改用户验证邮箱或设置用户密码；使用受控账户恢复流程。
- 首版不支持冒充用户登录、后台直接退款、修改余额、永久删除账户或批量禁用。
- 禁用账户不自动取消订阅或终止续费；界面明确提示订阅需另行处理。P0 只提供已确认的订阅关联信息和处理说明。
- 离线桌面使用和已签发离线许可的即时撤销无法由 Web 后台保证；显示“离线权限不受即时控制”，不宣称已封禁整个本地 App。未来如需支持，单独设计联网校验与许可吊销机制。

### 5.5 平台管理（P0 只读，P1 扩展）

- 查看咨询接收、身份认证、订阅网关是否已配置、最近检查时间和健康状态。
- 查看已接入网关的订阅及请求记录，保留来源 ID；必须先建立经验证的用户与订阅映射，未知归属不得猜测。
- 失败记录展示可供支持处理的错误摘要和请求 ID，不包含用户敏感原文或密钥。
- Provider 状态、额度和成本来自实际数据源；缺失成本显示 `unavailable`，不同币种不直接相加。
- P1 增加组织、云端项目及公开内容管理、公告与功能开关。仅管理已同步或已发布的对象；内容下架必须区分站点发布资源和客户本地文件。
- P1 的功能开关需保存草稿、预览影响范围、确认发布、记录版本并支持回滚。退款、扣费、额度调整单独立项。

### 5.6 系统设置与审计（P0）

- 可配置后台显示时区、咨询通知接收地址，并记录更改；通知接收地址须验证后才启用。
- 新咨询成功入库后才尝试发送运营通知。通知失败不撤销咨询，后台显示失败状态并允许重试；通知只包含编号和后台链接，避免发送完整个人信息。
- 通知重试去重，已成功送达的通知不重复发送；没有配置时显示“通知未配置”，咨询仍正常接收。
- 审计记录管理员身份、动作、目标、结果、发生时间、变更前后允许记录的字段、原因和请求 ID。
- 角色更改、登录与会话撤销、账户禁用恢复、咨询关联、客户合并与拆分、导入导出、机会阶段变化、报价及收款记录变更、任务完成与延期、联系方式展开、设置变更均需留痕。
- 普通后台操作不得修改或删除审计日志；不把密码、令牌、恢复链接或完整咨询正文写入审计。

### 5.7 数据导入与导出（P0）

- Super Admin 可导出当前筛选范围内的客户、咨询、用户或销售机会 CSV，导出前显示记录数、字段及“包含联系方式”开关，默认不包含联系方式。
- 记录导出人、条件、数量和时间；保护 CSV 单元格免受公式注入。
- 大批量使用异步任务；文件仅允许创建者在权限仍有效时下载，链接或文件 24 小时后失效。
- 任务失败显示失败原因与重试入口；不得展示成功下载按钮或生成半份文件而不说明。

- 支持通过 CSV 导入已有客户通讯录，首版每批最多 5,000 行；流程为上传 → 字段映射 → 校验与重复预览 → 确认导入 → 结果报告。
- 无联系方式、无效邮箱、重复或冲突记录逐行说明；不覆盖既有客户信息。确认后仅导入有效新记录，返回成功、跳过、失败的准确数量，失败行可单独修正重试。
- 导入批次和行记录具有稳定标识，重复重试不产生重复客户；来源标为导入并保留批次、操作人及原始来源说明。导入通讯录不创建注册账户或营销订阅。

### 5.8 统一客户档案（P0，CRM 核心）

**客户列表**：姓名、公司、邮箱或电话、来源、标签、优先级、是否已注册、开放机会数、最近人工联系时间、下一次跟进时间。默认提供“全部客户”“待跟进”“已注册”“有开放机会”“已有成交”视图，支持组合筛选。

**客户详情**分为基本信息、沟通时间线、销售机会、跟进任务和 App 账户。打开档案就能看到此人是谁、需求是什么、上次谈了什么、下一步做什么。

- 首版 Contact 代表一个自然人；基本信息包含姓名、邮箱、手机号、微信（选填）、职位、关联公司、来源、标签、优先级和内部备注。
- 基础公司档案包含公司名称、官网、行业、备注及联系人列表。一家公司可关联多个联系人；CRM 公司档案不自动成为 App 租户，也不授予公司成员任何权限。
- 官网咨询或验证注册触发客户建档；已有关联则复用同一档案。管理员也可手工添加尚未咨询、尚未注册的客户，例如活动认识、微信联系或转介绍。
- 新建客户至少提供姓名及一种联系方式；注册事件缺少姓名时允许显示“未填写”。只存储实际获得的信息，不从其他来源自动搜集补全。
- 标签可用于“开发商”“地产代理”“创意团队”等分类；优先级为高、中、低，默认中。已注册、是否有成交由关联记录计算，不用手工标签替代真实状态。
- 沟通记录支持电话、邮件、微信、会议和其他类型，记录实际发生时间、摘要、结果和录入人，可关联咨询或机会。外部应用中的发送和会面不会自动视为已发生。
- 时间线统一聚合咨询、人工沟通、任务、机会变化、注册及账户关键变更，标明来源；原始咨询不因修改客户资料而被覆盖。

**识别与合并规则**

- 已验证身份使用稳定用户 ID 关联；未验证的同邮箱咨询可归入同一联系档案供内部跟进，但保留“联系方式未验证”及来源，不构成身份确认。
- 共享邮箱、同名、手机号匹配或不同账户指向同一档案时提示潜在重复，人工核对；不能仅因公司域名相同合并客户或公司。
- 人工合并前预览字段冲突、咨询、任务、机会和账户关联，选择保留值并填写原因。保留原记录 ID、迁移映射和审计，误合并可按记录来源拆回，不丢失历史。
- 已关联不同注册账户的客户首版禁止直接合并，交由身份核验处理；合并客户不得合并登录身份、余额或订阅。

### 5.9 销售机会（P0）

销售机会记录一笔具体业务，例如“某开发商年度订阅”或“某项目内容服务”。同一个客户或公司可以有多条机会，复购新建机会，保留原成交记录。

| 阶段 | 进入条件 |
| --- | --- |
| 需求确认 | 已明确潜在业务，填写机会名称、主联系人和需求摘要 |
| 演示沟通 | 正在推进产品演示或方案讨论；已确认会议时间单独填写 |
| 报价中 | 已记录报价版本、金额、币种、报价日期和发送状态；草稿与已发送明确区分 |
| 商务确认 | 客户正在确认方案或条款，记录当前待办事项 |
| 已成交 | 已获得明确接受依据，填写约定金额、币种、成交日期及依据说明或引用 |
| 已流失 | 本次机会结束，填写原因和关闭日期 |

- 支持列表和看板；拖动与“更改阶段”表单具有相同校验和审计。允许跳阶段，但需补齐目标阶段必填信息；回退或重新打开关闭机会必填原因。
- 机会字段：名称、主联系人、关联公司（可空）、其他联系人、业务类型、需求摘要、阶段、预计金额与币种、预计成交日期、下一步动作、关联咨询、负责人。
- P0 负责人默认当前 Super Admin，团队分配放到 P1。未知金额允许留空，不估算成交概率或预测收入。
- 报价首版记录版本号、金额、币种、日期、有效期、说明和已有文件链接，历史版本不可覆盖；不要求生成报价 PDF、电子签约或开票。
- 实际收款按独立 PaymentRecord 记录金额、币种、日期、来源及凭证引用，可为人工记录或已核验 provider 数据；“已成交”本身不得自动生成收款。
- 收款摘要区分未记录、部分收款、已足额及超额待核对；以同币种已确认记录计算，无法核验的人工记录单独标记。退款和扣款操作仍不在本期范围。
- 关闭机会时提示处理关联未完成任务，可选择保留或取消，不静默删任务；机会成交不自动关闭未处理的咨询或开通订阅。

### 5.10 跟进任务与提醒（P0）

- 任务必关联客户，可进一步关联咨询或机会；包括标题、类型、负责人、截止时间、状态、完成结果和下一步。
- 状态为待完成、已完成、已取消；逾期由截止时间动态计算。延期保留原日期和原因，取消记录原因，完成记录实际时间和结果。
- 工作台支持今天、逾期、未来 7 天和全部任务。客户详情的“下一次跟进”取未完成任务中最早截止时间，已关闭咨询不再作为独立提醒来源。
- P0 提供站内到期提醒与未读标记；只有打开后台时接收和查看，不承诺浏览器关闭后的系统推送。P1 可增加邮件或日历提醒。
- 完成任务可创建下一次跟进，任务创建与完成均支持幂等重试。点击邮件或微信入口不自动完成任务。

## 6. 前后台数据闭环

### 6.1 咨询提交

1. 官网新增站内咨询入口，姓名、邮箱必填，公司与需求选填，手机号首版不必新增。
2. 服务端校验字段长度、邮箱格式和请求频率，防重复提交；提交处说明信息将用于处理本次咨询。
3. 持久化成功后返回咨询编号，页面显示“已收到咨询”；这不等于演示时间已确认。
4. 网络超时保留输入并用原幂等键重试，不能先显示成功。
5. 管理后台可查询该记录，异步发送通知；通知失败不影响接收结果。
6. 邮件备用入口明确说明需要用户自行发送；未接入邮箱时不追踪邮件是否收到。

### 6.2 注册和 App 身份

1. 用户提交注册请求，完成验证和条款确认后，身份服务创建稳定的 `user_id`。
2. 后台基于可靠事件或服务端查询同步账户，事件重复和乱序不能重复创建账户或覆盖新状态。
3. 将同邮箱咨询关联到用户；后台同时支持从咨询进入用户详情和从用户查看咨询历史。
4. App 在线受保护请求采用可关联至 `user_id` 的身份；订阅另以显式映射关联，不能仅靠客户端上传邮箱确定归属。
5. 同步故障可重试并定期对账；后台显示同步时间和异常，不能静默漏掉注册用户。

### 6.3 CRM 日常工作闭环

1. 新咨询、验证注册或管理员录入产生或关联 Contact；Contact 是客户档案，User 是登录账户，不能互相替代。
2. 管理员从工作台打开客户，记录联系结果和下一次跟进；有明确业务需求时新建销售机会，普通咨询不强制创建机会。
3. 通过演示和报价推进机会，报价历史、沟通与待办持续保留在客户档案。
4. 获得明确接受后标记成交，收款另行记录；App 服务开通仍走真实授权或订阅流程。
5. 成交后继续建立交付或回访任务，新需求创建新机会；客户未注册、订阅失效或账户禁用都不删除 CRM 历史。

## 7. 核心数据模型（逻辑设计）

以下定义实体与关系，不要求按表名直接实现。

| 实体 | 核心字段 |
| --- | --- |
| Contact | id、name、email、phone、wechat、job_title、company_id、source、tags、priority、user_id（可空且唯一）、verification_state、created_at、updated_at |
| Company | id、name、website、industry、notes；仅为 CRM 公司档案，不等于 App 组织 |
| Opportunity | id、contact_id、company_id、name、business_type、stage、expected_amount、currency、expected_close_at、closed_at、agreed_amount、outcome_reason、acceptance_reference、owner_id |
| OpportunityContact / Inquiry | opportunity_id、contact_id 或 inquiry_id；关联多位联系人及多次咨询 |
| QuoteRecord | id、opportunity_id、version、amount、currency、issued_at、valid_until、send_status、reference_url、created_by |
| PaymentRecord | id、opportunity_id、amount、currency、paid_at、source、verification_status、evidence_reference、provider_record_id（可空）、created_by；更正保留历史，同 provider 记录去重 |
| FollowUpTask | id、contact_id、inquiry_id（可空）、opportunity_id（可空）、title、type、owner_id、due_at、status、completed_at、result、idempotency_key |
| CommunicationActivity | id、contact_id、inquiry_id 或 opportunity_id（可空）、channel、occurred_at、summary、result、created_by |
| ContactMergeRecord / ImportBatch | 原客户映射、冲突选择及迁移清单 / 导入批次与行结果；保留执行者和可追踪历史 |
| User | id、auth_subject、email、verified_at、name、status、registered_at、last_login_at、registration_source |
| RegistrationAttempt | id、email、verification_status、expires_at；不能算正式用户 |
| Inquiry | id、contact_id、name、email、phone、company、message、source、language、status、is_spam、received_at、created_at、idempotency_key；next_follow_up_at 从任务派生，user_id 从客户关联派生 |
| InquiryActivity | id、inquiry_id、actor_id、action、note、occurred_at；保留状态和关联历史 |
| AdminMembership | user_id、role、status、granted_by、granted_at；平台角色与客户组织角色分开 |
| SubscriptionLink | user_id、provider、subscription_id、verified_at、mapping_source；首版人工核验或可信服务端建立 |
| ConsentRecord | user_id 或 inquiry_id、用途、版本、选择、时间；咨询联系与营销订阅分开 |
| AuditEvent | actor_id、action、target_type、target_id、safe_changes、reason、result、request_id、created_at |
| Notification / ExportJob | 对象 ID、任务状态、重试次数、创建者、时间和结果引用；不持有明文凭据 |

Contact 与 Inquiry、Opportunity、FollowUpTask 为一对多；公司与联系人为一对多，机会还可关联其他联系人。Contact 与 User 首版可选一对一；客户可以没有登录账户，每个正式注册用户须关联一个客户档案，关联异常进入待核对队列。User 与 Inquiry 通过 Contact 关联，禁止同时维护两套冲突映射。用户可关联多条订阅，但不得未经证据把一个订阅绑定给多个不相关个人。App 组织及权限成员关系在 P1 正式建模，与 P0 的 CRM 公司档案分开。

咨询、用户、活动、审计和任务状态应使用可事务化的持久存储。现有文件型订阅账本不是完整运营数据库；如仍保留，应通过服务端适配读取并定义同步与对账方式。

## 8. 页面体验和数据保护要求

- 表格配搜索、少量常用筛选、明确主操作；详情用概览和时间线，避免一次展开全部字段。
- 联系方式列表默认脱敏，具备权限的管理员可展开查看并留痕；详情访问同样受服务端权限控制。
- 加载、无记录、筛选无结果、无权限、失败和数据未接入使用不同状态。失败不能显示空列表冒充无数据。
- 360px 手机宽度优先显示姓名、状态、时间和跟进入口；电脑支持完整表格；键盘可完成登录、搜索和跟进。
- 保存期间禁止重复操作，失败保留输入；并发修改提示记录已更新，要求刷新核对，不静默覆盖他人变更。
- 咨询联系用途与可选营销订阅分别记录；不因注册或咨询自动同意营销。
- 提供明确的保留、匿名化和删除处理方案作为上线准备项；具体期限由业务方确认。删除流程保护审计与必要账本，按批准策略去除可识别信息，P0 由受控运维执行。
- 分析事件不携带姓名、邮箱、手机号和咨询原文；备份与访问权限需经恢复演练验证。

## 9. 非功能目标

以下为待验证的验收目标，不是现有性能承诺。

- 在约定测试环境和 10 万用户、10 万咨询数据下，常用列表查询 P95 ≤ 2 秒；搜索、分页由服务端执行。
- 咨询持久化成功后 5 秒内可在刷新后的后台查询；用户注册事件成功后 60 秒内可查询，超时显示同步异常。
- 禁用确认成功后，新在线受保护请求立即按禁用状态拒绝；现有在线会话在 60 秒内失效。若无法达到，禁用状态必须显示“执行中/失败”，不得提前显示完成。
- 管理数据可备份恢复，试运行目标 RPO ≤ 24 小时、RTO ≤ 4 小时；正式服务目标在部署方案中确认。
- 关键写入和审计必须一致完成，失败可追踪、可安全重试；咨询成功不依赖邮件供应商正常。

## 10. 验收标准

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| A01 | 普通用户直接请求后台 API | 返回无权限，无任何后台数据；修改前端角色无法绕过 |
| A02 | 管理员登录 | MFA、退出、过期与恢复流程实际可用；日志不泄露凭据 |
| A03 | 官网提交咨询 | 真实服务端保存，返回编号，后台可见，刷新仍在 |
| A04 | 超时后重试相同咨询 | 只生成一条记录；新的独立需求仍可生成另一条 |
| A05 | 通知发送失败 | 咨询仍在，后台标明失败，重试不重复发送成功通知 |
| A06 | 邮件备用入口 | 只打开邮件草稿，不显示已收到、不增加后台咨询数 |
| A07 | 跟进与关闭后重开 | 时间线保留全过程，原因、演示时间和到期跟进规则有效 |
| A08 | 未验证和已验证注册 | 未验证不计入注册数；验证成功后账户可查，重放事件不重复计数 |
| A09 | 咨询与注册关联 | 同验证邮箱可关联；姓名相同不误关联；改邮箱和手工撤销不丢历史 |
| A10 | 禁用及恢复用户 | 新登录和在线 API 受控、会话失效；恢复不复活旧会话；订阅与离线边界提示准确 |
| A11 | 仪表盘口径 | 卡片与相同条件的明细一致，跨时区边界正确，垃圾咨询被排除 |
| A12 | 数据源异常 | 显示失败、未接入或过期状态，不能显示伪造的 0、收入或项目数 |
| A13 | 导出 | 筛选一致、联系方式选项有效、权限与过期下载被拒绝、导出有审计 |
| A14 | 并发修改 | 旧版本提交不会静默覆盖新版本，错误后输入不丢失 |
| A15 | 全链路体验 | 真实浏览器完成咨询、注册、后台关联、跟进、禁用和恢复；手机可查阅与跟进 |
| A16 | 恢复和持久化 | 服务重启不丢记录；备份恢复后关键记录、关联和审计一致 |
| A17 | 多渠道客户建档 | 咨询、注册、手工录入和 CSV 导入均有来源；同一已识别客户复用档案，重复事件不增客户数 |
| A18 | 客户完整视图 | 一个档案可看到咨询、沟通、任务、多个机会和注册账户；未注册客户也能完整跟进 |
| A19 | 合并与拆回 | 冲突预览、历史迁移、审计和拆回有效；不同登录账户不能被误合并 |
| A20 | 机会阶段与报价 | 看板和表单同样校验，报价版本保留，成交依据必填；注册和咨询完成不会自动成交 |
| A21 | 成交与收款 | 成交金额不充当收入；未知金额、不同币种、人工未核验收款分别展示，provider 重放不重复入账 |
| A22 | 跟进和提醒 | 今日、逾期和客户下一次跟进一致；咨询预约跟进只生成一份任务；延期、完成、取消均留痕 |
| A23 | 客户导入 | 预览与确认结果一致，错误逐行报告，重试不重复创建；不产生登录账户或营销订阅 |
| A24 | CRM 完整业务闭环 | 手工添加未注册客户，记录沟通、创建任务和机会、报价、成交、记录收款，之后注册仍复用原客户档案 |

安全测试使用独立普通用户、Super Admin 和禁用账户；数据核验使用可追踪测试记录。Mock 页面、接口单测和截图不能替代真实持久化及端到端验证。

## 11. 实施顺序与阶段交付

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| 1. 基础与接入 | 管理员身份、CRM 数据库、咨询接收、注册验证、统一客户建档、审计 | 两类入口真实持久化并关联客户；普通用户无后台访问权限 |

| 4. 扩展运营 | 多角色协作、App 组织、云端项目与内容、运营分析、自动提醒 | 单独补充操作范围和验收后实施 |

首版必须交付可日常使用的 CRM。自动群发营销、邮箱及微信内容自动同步、电子签约、财务开票、自动扣费或退款、远程读取本地项目、远程执行生成任务和后台替用户使用 App 不在本期范围。

## 12. 成功评估与待定项

上线后重点观察咨询入库成功率、待处理咨询积压、首次人工跟进耗时、跟进任务逾期率、机会成交与流失数、注册数据同步延迟和管理员完成一次查询/跟进的耗时。任务逾期率以所选截止时间段内未取消的任务为分母，截止前未完成的任务为分子；保留历史截止时间以防延期改写历史。先建立基线，再确定业务目标，不虚构转化提升比例。

P1 可计算“咨询后注册转化率”：分母为所选咨询时间段中按规范邮箱去重的有效咨询人群；分子为其中在首次咨询后 30 天内完成验证注册的人数。排除咨询前已注册者，观察窗口未满的人群单独标明，不能把所有关联用户都算新增转化。

以下决策不阻碍 PRD 评审，但实施相关部分前需要落实：

1. 确认站内咨询接收作为新增渠道的实施方案，及现有邮箱是否只作备用；首版不默认读取邮箱历史。
2. 选择身份服务、注册开放方式和首个 Super Admin 的明确身份。
3. 确定部署环境、正式域名和通知接收地址；未确定前不写成已上线服务。
4. 确定首批接入的 App 在线服务、用户与现有订阅的核验映射、离线许可保留边界。
5. 确定个人信息保留期限和删除处理负责人。
