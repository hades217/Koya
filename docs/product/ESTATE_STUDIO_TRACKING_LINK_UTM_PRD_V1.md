# Estate Studio Tracking Link、UTM 与销售归因 PRD

- 版本：V1.0
- 日期：2026-09-06
- 状态：需求稿；本次只编写 PRD，不代表已开发、埋点已接入或已上线。
- 适用产品：官网、受控落地页、Super Admin CRM。
- 产品负责人：Super Admin。
- 关联文档：[Super Admin / CRM PRD](ESTATE_STUDIO_SUPER_ADMIN_PRD_V1.md)。

## 1. 要解决的问题

负责人需要在网页后台创建和管理推广链接，知道哪个活动、页面、素材、员工或转介绍伙伴带来访问与 Leads；随后追踪 Sales 如何推进到成交，并将来源证据连接到现有销售漏斗和佣金规则。

核心闭环：**活动与人员 → Tracking Link / 二维码 → 落地页访问 → 咨询或注册 → 有效 Lead → 销售机会 → 成交或流失 → 佣金归属核对。** 注册不是销售必经阶段，也不能当作成交。

产品必须分别回答：

1. 哪些渠道、活动、页面和素材带来了访问与有效 Leads？
2. 哪个获客人员贡献了这些 Leads，证据是什么？
3. 哪个 Sales 跟进了商机，其分享链接是否被访问，最终是否成交？
4. 流失发生在哪个阶段，CRM 中记录了什么客户反馈？
5. 哪些归属可以用于佣金核对，哪些存在冲突、缺失或人工更正？

**UTM 是来源标签，不是身份凭证、成交证明或佣金凭证。** 访问下降只能定位可能的问题，不能自动断言客户流失的原因。

## 2. 当前基础与本次边界

本地代码已具备客户、咨询、注册用户、商机阶段历史、漏斗分析、员工/伙伴、渠道佣金规则和佣金测算。商机已有 `lead_staff_id`、`sales_staff_id`、`lead_channel` 与 `commission_snapshot`；成交后锁定佣金归属。当前漏斗以已录入商机为基础，尚未覆盖匿名获客行为。

本 PRD 增加链接管理、网页埋点、身份关联与归因证据。沿用现有业务记录，不另建一套重复的客户、销售或佣金账本。实施前须重新确认官网表单、注册服务和部署域名的实际接入状态。

| 优先级 | 范围 |
| --- | --- |
| P0 | 活动/链接管理、链接版本、二维码、受控页面目录、同站追踪、服务器转化事件、Lead 归属确认、Sales 分享触点、报表与诊断、归因更正审计 |
| P1 | 员工受限账户、跨受控域名追踪、GA4 事件镜像与核对、广告成本导入、离线活动批量导入 |
| 不在本期 | 跨设备匿名识别、浏览器指纹、广告平台自动归因、自动发放佣金、多获客人分佣、第三方任意网页注入脚本 |

P0 由 Super Admin 代员工生成链接并设置分享人；员工档案不等于登录账户。未接入追踪脚本的外部页面只报告链接跳转请求，不声称能追踪其页面行为。

## 4. 三类业务场景

### 4.1 Marketing、地推、运营、转介绍获客

管理员选择活动、页面、渠道、获客人员和素材，生成专属短链与二维码。一个员工可持有多个链接；同一活动为不同员工/素材生成独立链接，以免混淆贡献。

线下地推在展台或传单上放二维码。扫码打开网页后进入同一追踪流程；扫码不等于到场人数，二维码图片被下载也不等于扫码次数。

### 4.2 Sales 跟进

在商机详情点击「生成销售跟进链接」，默认带入商机、Sales、活动或沟通目的、目标页面。用途固定为 `sales_followup`，与获客 `acquisition` 区分。

公开链接仅包含不可枚举的追踪标识，不包含客户名、联系方式、商机编号、金额或报价访问权限。访问记录首先显示「该商机分享链接被访问」，只有访客身份独立验证且与客户匹配，才能显示「已验证客户访问」。链接被转发给第三人时不能冒认原客户。

### 4.3 负责人复盘与佣金核对

负责人从活动报表查看有效 Leads，再进入客户/商机详情查看完整触点。原获客证据与后续 Sales 助攻并列显示。佣金使用经确认的获客人与成交 Sales，UTM 不直接修改佣金快照。

## 5. 链接创建与生命周期

创建流程：选择页面 → 选择用途 → 填写渠道／来源、UTM Medium、UTM Content、UTM Campaign → 选择获客类型与分享人员 → 预览 → 保存 → 复制链接/下载二维码。

表单必须明确呈现四个主要字段：**渠道／来源（UTM Source）、UTM Medium、UTM Content、UTM Campaign**，不能藏在高级设置里。必填：名称、活动、目标页面、用途、获客类型、分享人、source、medium、campaign；content 字段始终可见，允许在没有素材区分时留空。campaign 名称和 campaign ID 由选择的活动带入，选择其他 campaign 时同步切换活动，不形成两个冲突值。获客人员停用后不得生成新链接；历史链接不自动转归其他人。

首版使用系统批准的 HTTPS 域名与路径；开发环境可单独放行明确的本机地址。禁止任意外部重定向、`javascript:` URL、URL 用户名密码及未批准域名。链接管理不赋予私有报价或客户页面的访问权限。

### 链接状态

- 草稿：可以修改，不能用于公开投放。
- 启用：允许跳转和追踪。
- 停用/到期：展示统一结束页和普通官网入口；不将该请求计入有效活动访问。
- 归档：从默认列表移除，历史数据保留，不硬删除。

首次启用后，活动、用途、分享人和 UTM 归属不直接覆盖。需要变更归属时「复制为新链接」，生成新 ID。仅修复目标页面时发布新版本，历史点击保留当时版本和目标页面。测试流量带明确测试标志，不计业务报表。

示例格式（域名仅为占位，非已部署链接）：

```
https://tracking.example/r/<opaque-link-code>
https://www.example/landing?utm_source=wechat&utm_medium=social&utm_campaign=studio_launch&utm_id=cmp_001&utm_content=video_a&trk=<opaque-link-code>
```

短链与完整 UTM 链接均可使用。完整链接直接抵达页面，不应因少一次跳转而漏记页面会话；跳转请求与页面访问是独立指标。

## 6. UTM 字典与管理约束

Google 的手工标记文档将 UTM 用于来源、媒介、活动等维度；本产品在此基础上增加统一命名和内部人员映射。以下必填与命名规则为本产品要求，并非声称所有分析平台都强制要求。[Google：手工流量来源标记](https://support.google.com/analytics/answer/11242870?hl=en)、[Google：Campaign URL Builder](https://support.google.com/analytics/answer/10917952?hl=en)。

| 参数 | 含义 | 产品规则 / 示例 |
| --- | --- | --- |
| utm_source | **渠道／来源**：平台、合作方或活动来源 | 必填；`wechat`、`linkedin`、`brisbane_expo` |
| utm_medium | 传播方式 | 必填；受控字典 `social`、`paid_social`、`email`、`qr`、`referral`、`sales_outreach` |
| utm_campaign | 活动名称 | 必填；从活动 slug 带入，如 `studio_launch` |
| utm_id | 稳定活动 ID | 系统生成，与活动更名解耦 |
| utm_content | 素材/展位/版本 | 可选；`video_a`、`booth_02` |
| utm_term | 关键词 | 可选；不填写客户输入或联系方式 |
| trk | 本系统链接代码 | 自定义参数，不是标准 UTM；仅作服务端链接映射，不授予权限 |

UTM 使用统一小写 ASCII slug，建议只允许字母、数字、下划线和连字符，单字段最长 100 字符；中文展示名与 slug 分开保存。统一使用 URL API 编码，保留批准的业务查询参数和 hash。目标 URL 已有冲突 UTM 时显示差异并要求在保存时选择规范值，禁止静默重复拼接。

### 四个主要字段的完整示例

| 场景 | 渠道／来源（utm_source） | UTM Medium | UTM Content | UTM Campaign | 业务获客类型 |
| --- | --- | --- | --- | --- | --- |
| 微信推广视频 | `wechat` | `social` | `video_a` | `studio_launch` | Marketing |
| 展会二维码 | `brisbane_expo` | `qr` | `booth_02` | `studio_launch` | 线下地推 |
| 运营邮件 | `customer_newsletter` | `email` | `demo_cta` | `reactivation_sep` | 运营 |
| 合作伙伴转介绍 | `partner_001` | `referral` | `intro_card` | `partner_program` | 转介绍 |
| Sales 演示邀请 | `sales_team` | `sales_outreach` | `demo_invite` | `demo_followup` | 按原 Lead 保留；链接用途为销售跟进 |

以上均为规则示例，不是已配置的投放渠道。员工身份通过链接服务器映射，不把姓名或邮箱填入 UTM Content。列表、详情、筛选、导出和报表均提供这四个维度。

界面另列「获客类型」，对应现有业务渠道 `Marketing / 线下地推 / 运营 / 转介绍 / Sales 自拓 / 其他`，与 UTM Source 和 UTM Medium 分开。例如「运营」可以通过 `email` 或 `social` 获客，不能用 medium 直接判断员工职责。

有有效 `trk` 时，CRM 用服务器登记的链接版本认定链接归属；客户端 UTM 不一致时记为冲突并显示规范值与净化后的提交值。只有 UTM、没有有效链接代码时可分析流量来源，但人员归属为未知。复制他人的有效链接仍只能证明该链接被使用，不能证明实际分享人。

## 7. 网页追踪与事件定义

所有受控页面安装统一 SDK。页面登记只说明配置存在；必须收到有效测试事件后才显示「已验证接入」，并显示最近事件时间。SDK 故障不得阻止浏览、咨询或注册。

| 事件 | 来源 | 触发条件 / 口径 |
| --- | --- | --- |
| redirect_request | 跳转服务 | 每次短链请求；原始请求可含机器人和预览抓取，不称为真人点击 |
| landing_view | 浏览器 | 页面实际载入且满足采集条件；会话首次落地 |
| page_view | 浏览器 | 已载入页面或 SPA 有效路由变化；使用 page_id 去重上报重试 |
| cta_click | 浏览器 | 受控 CTA，如预约、注册、联系；不等于完成咨询 |
| form_start | 浏览器 | 首次交互表单；不采集字段内容、输入值或按键 |
| inquiry_created | CRM 服务端 | 咨询事务成功落库；同一请求幂等键只计一次 |
| registration_verified | 身份服务 | 邮箱验证完成，注册成功；不按注册按钮点击计算 |
| lead_qualified | CRM 服务端 | 首次人工确认为有效 Lead；必须有处理记录 |
| opportunity_created | CRM 服务端 | 商机成功建档，并保留关联 Lead |
| stage_changed | CRM 服务端 | 保存成功的阶段历史，复用现有原因记录 |
| opportunity_won / lost | CRM 服务端 | 有效成交/流失变更；当前状态报表按商机去重，事件报表保留重开历史 |
| payment_verified | 支付接入服务，P1 | 支付来源确认；现有人工未核验收款不能触发 |

通用字段：`event_id`、`schema_version`、`occurred_at`、`received_at`、`site_id`、`page_id`、净化路径、可用时的匿名 visitor/session ID、link ID/version、touch ID、来源维度、采集许可状态、测试/机器人标志。客户、Lead、商机关联 ID 仅由服务端授权流程附加；浏览器不得伪造业务转化、员工或成交金额。

采集失败可短暂排队重试，但不延迟用户提交；事件按 event_id 幂等。业务转化通过同事务 outbox 在落库后发送，避免表单成功但转化丢失。报告同时保留事件时间与接收时间，迟到事件标注修订时间。

## 8. 匿名访问、身份关联与有效 Lead

### 8.1 会话与触点

本 CRM 提议采用 30 分钟无活动结束会话，同会话内发生新的有效推广入口时新增触点，不自动增加会话。连续内部浏览不产生新的获客触点。内部菜单和 CTA 使用事件 ID，不追加 UTM 覆盖来源。此为本 CRM 口径，GA4 数值不承诺逐项相同。

直接访问不覆盖已有合格来源；没有来源证据时显示 `direct / unknown` 并给出细分状态。缺失 UTM、用户拒绝采集、参数被平台移除、未接入 SDK、机器人过滤等各有独立诊断状态，不统一伪装为直接访问。

### 8.2 身份关联

提交咨询时，将服务器认可的 touch/context 与咨询一起保存；验证注册后通过受控身份流程关联账户。同邮箱按 CRM 现有合并规则处理，共享邮箱冲突保留人工核对。匿名历史只能关联已获得许可且有确定性证据的同浏览器上下文，禁止基于 IP、姓名相似或设备指纹合并用户。

同一客户可有多个 Lead 和多个商机。新增 Lead 实体表示一轮明确需求：一条咨询默认创建一个待判定 Lead；同轮重复咨询可人工关联既有 Lead，并保留原始提交。纯注册只建立注册转化，不自动记为有效 Lead。电话/现场线索可以手工建 Lead，来源标为人工记录，无网页访问证据时不补造访问。

Lead 状态：待判定、有效、无效、重复。有效判定需确认存在可跟进的业务需求与联系途径；无效/重复需原因。重复 Lead 关联保留 Lead 后，报表只计算保留记录，历史判断写审计。

## 9. 归因规则：流量、获客、成交分别记录

### 9.1 归因窗口与报表模型

P0 建议默认归因窗口为 Lead 创建前 30 天，属待确认业务参数。管理员可设置 7/30/90 天，保存 policy_version；规则变更仅影响之后创建的 Lead。历史重算必须作为单独分析视图，不能覆盖业务归属。

每个 Lead 保存：窗口内首次合格触点、末次非直接合格触点、全部辅助触点、来源完整性和规则版本。首次可观察触点不等于用户真正第一次接触品牌；无窗口内证据为未知，不向历史无限追溯。

Marketing 报表提供首次与末次非直接触点两种视图，各自独立计算，不能相加。首次归因默认用于获客人建议；Sales 跟进用途不参与覆盖既有 Lead 获客归属。

### 9.2 业务归属

| 字段 | 确定方式 | 变更规则 |
| --- | --- | --- |
| 建议获客人 | 首次合格 acquisition 链接的登记人员 | 仅建议；携带证据与冲突状态 |
| 确认获客人 | Super Admin 接受建议或人工指定 | 必须保存确认人、时间、理由与证据 |
| 成交 Sales | 商机明确分配的 Sales | 不能从最后一次链接点击自动替换 |
| Sales 助攻触点 | sales_followup 链接被访问 | 与原获客记录并存，不自动新增佣金 |
| 佣金归属 | 现有商机归属与规则快照 | 成交后沿用已有锁定机制，UTM 不得绕过 |

在商机选择主 Lead；P0 一个商机只有一个主 Lead，可附加辅助证据。一个 Lead 可产生多个真实商机，报表分别展示「产生商机的 Lead 数」和「商机数量」。商机未关联 Lead 时计入销售总览，但不分配到某个营销链接的归因成交中。

获客归属确认后不因再次点击其他链接自动改变。成交前更正需权限、理由、前后值和证据；成交后只能进入归属争议记录，P0 不直接修改锁定佣金或自动重结算。重复 Lead 合并、客户合并、跨活动再次咨询均不得静默覆盖来源。

## 10. 报表口径与分析路径

### 10.1 网页表现：按访问会话日期

按页面/链接/活动查看有效会话、页面浏览、CTA 点击、开始填表会话、成功咨询会话及注册验证会话。访问数排除明确识别的测试/机器人，但不宣称过滤后全是真人。

同一可测会话内：

- CTA 点击率 = 点击该 CTA 的会话数 ÷ 看到对应页面的有效会话数。
- 咨询转化率 = 成功创建至少一条咨询的会话数 ÷ 看到咨询落地页的有效会话数。
- 表单完成率 = 已开始表单且成功提交的会话数 ÷ 已开始表单的会话数。

缺少浏览器事件但服务端咨询成功时，保留真实咨询总量，标记「无法关联访问」；不塞进会话转化率分子。多次提交不让会话率超过 100%。

### 10.2 获客与销售：按 Lead 创建批次

选择一段时间内创建的非重复 Lead，追踪到当前报告时间。展示有效率、Lead→商机率、有效 Lead→成交率、关联商机当前赢单率、成交金额、阶段流失原因及佣金测算。

- 有效率 = 当前有效 Lead 数 ÷ 本批非重复 Lead 数。
- Lead→商机率 = 产生至少一个商机的有效 Lead 数 ÷ 本批有效 Lead 数。
- 有效 Lead→成交率 = 至少一个关联商机当前已成交的有效 Lead 数 ÷ 本批有效 Lead 数。
- 商机赢单率 = 当前已成交商机数 ÷ 当前已成交与已流失商机数之和。

未结案数量必须单列；短期批次尚未成熟不能直接判定渠道无效。多个 Lead/辅助触点不得重复分配同一笔商机成交金额。不同币种分组，约定成交金额与核验到账金额分开；未接支付来源时到账显示 unavailable。

### 10.3 人员与失败原因

获客员工表：所属渠道、有效 Leads、产生商机的 Leads、关联成交、确认/待确认归属与获客佣金测算。Sales 表：分配商机、联系/演示/报价阶段、赢单率、跟进触点与成交佣金测算。点击任意指标可查看构成记录及其筛选口径。

优先显示可行动信息：高访问低咨询的页面、有效率较低的活动、长时间未跟进的 Leads、进入报价后流失的商机。展示客户原始反馈和记录时间；没有反馈显示「原因未记录」，不由点击轨迹生成确定性原因。

分母为 0 或数据不可用时显示「暂无样本 / unavailable」，不显示推测的 0%。P0 不提供缺少真实成本数据的 CAC/ROAS。

## 11. 数据结构与接口边界

| 对象 | 核心字段 |
| --- | --- |
| campaigns | id、name、slug、channel、owner、status、起止时间 |
| tracked_pages | site_id、page_id、name、path、允许域名、接入状态、last_event_at |
| tracking_links / versions | opaque_code、campaign、page、purpose、staff、规范 UTM、目标 URL、状态、生效时间、version |
| tracking_sessions / touches | 匿名标识、session_id、link/version、净化来源、触点时间、采集许可、质量标志 |
| tracking_events | event_id、schema、事件类型、occurred/received 时间、touch、服务端业务关联 |
| leads | contact_id、主咨询、资格状态、主需求、原始来源快照、确认获客归属、policy_version |
| attribution_decisions | Lead/商机、模型、来源触点、更正前后值、操作者、理由、证据 |
| opportunities 扩展 | primary_lead_id、辅助触点引用、继承归属证据；保留现有 Sales 与佣金字段 |
| conversion_outbox | 业务唯一键、事件、发送状态、重试次数 |

接口示意：管理员 `/api/tracking/campaigns`、`/links`、`/pages`、`/reports`、`/attributions`；公开 `/r/:code` 与受限 `/tracking/events`。实际路径和 SDK 接入域在设计评审确定。

浏览器上报仅允许网页事件白名单；事件时间、大小、频率、site/domain 及上下文有效性均校验。公开采集端不能只依赖可伪造的 Origin 判断可信业务转化。咨询/注册/成交事件只能由业务后端 outbox 产生，且幂等键绑定实际记录。

## 12. 权限、数据最小化与安全

P0 管理、导出、人员映射和归属修改仅开放 Super Admin；未来员工只能查看授权记录，不可修改自己的计佣归属。敏感导出和人工归属更正写审计。

Google 明确要求不得把可识别个人的信息放入发送给 Analytics 的 URL 或 campaign 参数。因此 UTM、公开短链、GA4 事件不包含姓名、邮箱、电话、微信号、客户备注或报价内容。[Google：避免发送 PII](https://support.google.com/analytics/answer/6366371?hl=en)。

SDK 使用页面 ID 与净化路径，不上传完整任意查询串、表单值或 URL hash；认证 token 不进入事件、日志或 Referrer。分析 Cookie/跨页面关联依据产品最终批准的采集许可策略启用；拒绝时不使用持久分析 ID 或指纹替代，保留必要业务提交并标明追踪缺失。对第三方分析的发送独立受控。

拟议原始网页事件保留 90 天、按日匿名汇总 13 个月；客户与销售业务记录沿用独立保留规则。这些是产品建议值，不是法律结论，实施前需确认适用策略。删除/撤回身份关联应覆盖事件映射、导出及第三方同步队列，同时避免把匿名汇总重新识别到个人。

短链不能成为开放重定向；参数异常降级到允许页面或明确错误页，不跳往提交者提供的任意地址。限流、已知机器人/链接预览标识和内部测试排除均需可诊断，原始请求与过滤结果分开统计。

## 13. P0 验收条件

1. 管理员可为同活动创建不同员工、渠道、素材的链接和二维码；表单、列表、详情与报表明确提供渠道／来源、UTM Medium、UTM Content、UTM Campaign，生成 URL 与所填值一致，页面、分享人与版本可核对。
2. 启用链接的归属不可直接覆盖；复制生成新代码，目标修复保留历史版本。
3. 长 URL 已有 query/hash 时生成结果合法；冲突 UTM、重复参数、个人信息与非批准域名被阻止或要求修正。
4. 普通访问、二维码访问、直接完整 UTM 访问都能形成正确触点；预览抓取不被当作确定真人访问。
5. 一次表单重试只产生一条咨询转化；点击后提交失败不计咨询成功；验证邮箱前不计注册成功。
6. 拒绝追踪、SDK 被拦截或采集服务失败时，咨询和注册仍成功，报表显示无法关联访问。
7. Lead 首次/末次非直接模型可对比；直接访问、内部 CTA 和后续 Sales 链接均不覆盖已确认获客人。
8. UTM 被改写或 `trk` 无效时标记异常，不更改员工/佣金；转发 Sales 链接不冒认原客户身份。
9. 同一客户重复咨询、多个 Leads、多个商机和跨员工冲突均保留历史；成交金额在单一归因模型内不重复计入。
10. 获客人和成交 Sales 可为不同人或同一人；归因确认连接现有规则快照，成交后无法用追踪接口改佣金。
11. 零样本、未知来源、未结案、金额未知和多币种展示正确；网页会话批次与 Lead 批次不混用。
12. 每个报表指标可以下钻到一致的记录列表；更正后展示修订时间、原值和操作者。
13. URL、事件、日志不含表单联系方式与认证信息；匿名请求不能读取人员映射或创建业务转化。
14. 测试覆盖跨天、窗口边界、晚到事件、重复事件、过期/停用链接、参数清洗、会话超时及采集许可切换。
15. 建议验收负载：100 万网页事件、1 万条链接；典型报表 P95 ≤ 2 秒，转化落库至报表可见 ≤ 60 秒；在明确测试环境、数据量和并发下记录实测值，未测不得声称达标。

## 14. 实施顺序与发布闸门

1. 确定采集域名、许可策略、归因窗口和 Lead 定义；完成 schema、事件字典和服务器 outbox 设计。
2. 实现后台页面目录、活动/链接管理、版本与二维码，先用隔离测试数据核对跳转。
3. 接入官网 SDK、咨询与注册事件；验证数据最小化和采集失败不影响业务。
4. 加入 Lead 资格判断、来源建议/确认、商机关联与 Sales 分享链接。
5. 实现两类 cohort 报表、来源诊断和佣金归属核对；完成端到端验收后再发布。

上线前必须有真实受控域名、实际表单后端接入、管理员鉴权、追踪许可实现和公开页面读回证据。当前本地 CRM 运行不代表这些条件已满足。首版自有事件库与 CRM 作为业务转化依据；GA4 可后续接入辅助分析，不能替代业务账本。
